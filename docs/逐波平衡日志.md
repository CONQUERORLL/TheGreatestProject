# 逐波平衡日志（`user://balance_log.json`）

> 2026-09-17 第 8 轮需求 4 落地。**代码是唯一真值**，本文只解释「日志里有什么、怎么读」，
> 数值口径全部写进 `game/scripts/systems/balance_log.gd` 的注释里，两边不一致时以代码为准。

## 一句话

**每一波结束、写存档的同一刻**，把「这一波收尾时的全部数据」（玩家属性 / 武器 / 道具 /
法宝 / 本波战斗统计）写进一份 JSON；配 `game/tools/balance_report.py` 可以直接打印成表，
用来复盘「第几波开始掉队、是哪把武器在输出、承伤从哪一波开始压不住」。

## 位置与落盘点

| 项 | 值 |
|---|---|
| 游戏内路径 | `user://balance_log.json` |
| Windows 实际路径 | `%APPDATA%\Godot\app_userdata\BrotatoLite\balance_log.json` |
| 实现 | `game/scripts/systems/balance_log.gd`（`class_name BalanceLog`，静态工具类，不是 autoload） |
| 常规落盘 | `main._finish_evolve_flow()` —— 紧跟 `SaveRun.save()`，即「收波 → 掉落回收 → 进化结算 → 存档」之后 |
| 额外落盘 | 阵亡（`outcome="death"`）、通关（`outcome="victory"`） |
| 清空时机 | 新局开始（`main._ready` 新局分支）；续档则**接着写**，保留前面几波的历史 |

**为什么钉在存档点上**：这样「日志里记录的玩家状态」与「读档得到的玩家状态」是同一时刻的
同一份数据，不会出现「日志说 A、读档是 B」这种没法分析的分叉。

**与存档的关系**：两者是**独立文件**。阵亡 / 通关时存档会被清掉，日志**刻意保留** ——
「死在第 N 波的什么构筑」正是分析要的样本。

## JSON 结构

```
{
  "version": 1,
  "updated_at": "2026-09-17T23:12:03",   // 最近一次落盘时间
  "latest": { ... },                     // 最新一波的**全量**快照
  "waves":  [ ... ]                      // 逐波**紧凑**历史（默认保留最近 120 波）
}
```

### `latest` = 最新一波全量快照

| 字段 | 内容 |
|---|---|
| `wave` / `outcome` | 波号 / `shop`（正常收波）· `death` · `victory` |
| `run` | 难度 id+名、角色 id+名、无尽/每日、`run_time`、等级、经验、材料、累计击杀、积分、地图主题、区域元素、`run_rules`（自定义开局规则） |
| `wave_data` | 本波战斗统计，见下表 |
| `player` | 玩家快照：`hp`/`max_hp`/`element`/`sigil`/`char_trait`/`skill`/`stats`（全量属性）/`weapons`/`items`/`artifacts`/`upgrades`/`family_synergy` |

`wave_data`：

| 字段 | 口径 |
|---|---|
| `duration` | 本波**战斗时长**（`GameState.run_time` 只在 PLAYING 累加 → 不含 intro 与商店） |
| `duration_wall` | 上一次落盘到本次落盘的**墙钟**时长（含 intro / 商店 / 升级选择） |
| `kills` / `spawned` | 本波击杀数 / 本波出怪数（差值是逃跑或未清完的） |
| `materials_gained` | 本波材料净增（掉落回收已结算，商店消费属下一波） |
| `damage_dealt` | 本波**打进血**的伤害总量（含暴击、经全部减伤/抗性、含击杀那一下的溢出伤害） |
| `damage_taken` | 本波玩家受击总量（**闪避成功不计**、无敌帧内不计） |
| `heal` | 只统计走 `player.heal()` 的即时治疗（**不含被动回血、吸血、事件直达 hp 的写法**） |
| `dps` | `damage_dealt / duration` |
| `hp_min` / `hp_end` | 本波最低血量（逐帧采样）/ 收波时血量 |
| `boss_wave` / `event` | 是否 BOSS 波 / 事件波类型（`treasure` · `hunt` · `meteor`） |
| `by_source` | 伤害**按来源拆分**：武器 id（`knife`…）· `trait` · `skill` · `status` · `artifact` · `other` |

`player.weapons[]` 每项：`id` / `name` / `count`（同名份数）/ `evolved` / `element` /
`family` / `attack_type` / `proj_kind` / `dmg` / `cd` / `cd_effective` / `reach` / `splash` /
`pellets` / `status` / `price` / `desc`。

- ⚠️ `cd_effective = cd ÷ as_mult`，与 `player.try_fire` 的算法一字不差。
- ⚠️ `reach` 由 `player.weapon_reach()` 计算，**内部调 `_weapon_runtime_cfg()`**（开火路径的同一个函数），
  所以它已含角色特性 / 道具加成；投射武器 = `bspeed × bullet_life + 26 + splash`，近战 = `range`。
- ⚠️ 刻意**不写「预估 DPS」**：日志只给原始因子（`dmg` / `cd_effective` / `stats.dmg_mult` /
  `crit_ch` / `crit_mult` / `element` / 同化度），分析脚本自己按口径算 —— 免得日志里的半成品
  DPS 与 `docs/武器DPS体检表.md` 的口径分叉，变成第二个"真值"。

### `waves[]` = 逐波紧凑历史

每波一条，含：`wave` / `outcome` / `at` / `duration` / `run_time` / `level` / `xp` /
`kills` / `spawned` / `materials` / `materials_gained` / `hp` / `hp_min` / `hp_max` /
`damage_dealt` / `damage_taken` / `heal` / `dps` / `by_source` / `weapons` / `items` /
`artifacts` / `stats`（14 个曲线属性 + 5 条 `assim_*` 同化度）。

全量 `stats` 只存在 `latest` 里、历史里只留曲线用得上的那些 —— 无尽局跑几十波时，
把每波的全量属性都存下来会让文件白白涨到几 MB。

## 怎么读

```bash
C:/Users/Administrator/.workbuddy/binaries/python/versions/3.13.12/python.exe \
    game/tools/balance_report.py                # 自动定位 user://balance_log.json
... game/tools/balance_report.py <path.json>    # 或指定文件
```

输出两块：

1. **逐波曲线**：波号 / 等级 / 击杀 / 出怪 / DPS / 总伤害 / 承伤 / 回复 / 最低血% / 材料 /
   本波材料 / 时长 / 武器构成；末尾附**掉队预警**（DPS 环比下滑 >15%、承伤环比放大 >1.5 倍、
   最低血量跌破 25%）。
2. **最新一波明细**：属性、同化度、武器实战参数（冷却 / 射程 / 溅射）、道具法宝清单、
   伤害来源占比。

分析时常用的三个判据：

- **DPS 是否跟得上波次**：波次越高怪越硬，DPS 曲线平了就是"构筑到顶了"。
- **承伤 vs 回复**：`damage_taken` 涨而 `heal` 不涨 → 该补生存；`hp_min` 长期贴地 → 该补容错。
- **`by_source` 占比**：某把武器占比 >60% 说明它是唯一支点（换掉就崩），
  多把武器各占 20~30% 才是健康构筑；`other` 占比异常高说明有伤害没被打上来源标签（见下）。

## 已知边界（写给以后的自己）

- **商店购买不算进本波**：`commit` 发生在进商店之前，买的东西体现在**下一波**的快照里。
  这样逐波曲线读起来干净（每波一条"这一波是怎么打的"），代价是没法从单条记录看出当前钱包变化。
- **`by_source` 的标签来源**：武器 id 由 `player._roll_damage` 写进 roll，逐级透传到
  `enemy.take_damage` 的第 5 参；特性 / 技能 / 状态 DoT / 法宝各自显式标注；**其余全归 `other`**
  （例如元素反应的连锁伤害、死亡爆炸、处决）。所以 `other` 占比高不等于漏记，但值得看一眼。
- **不改游戏状态**：`BalanceLog` 只读运行时真值，写盘失败只 `push_warning`，不阻断存档与玩法。
- **冒烟隔离**：`smoke_test.gd` 会把日志根切到 `user://tests/smoke_run/`，正式档不会被测试污染。
