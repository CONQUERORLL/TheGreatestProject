## 二、存档语义（checkpoint：wave_start → shop）　✅ **已在 S4.5 落地**（规划 §12.7 ③）

> ⚠️ **本节的预判有两处被推翻 —— 见 §2.1 表下的说明，别照着「五处全改」抄。**

### 2.1 五处写入点　→ **实际只改了 3 处**

| 位置 | 现状 | 改成 | 不改的后果 |
|---|---|---|---|
| `main.gd:141` | 新局首波 `SaveRun.save(1, player, CHECKPOINT_WAVE_START)` | ~~`CHECKPOINT_SHOP`~~ → **实际保留 `WAVE_START`** ⛔ 预判有误 | 若真改了 → 恢复时去开一个不存在的「第 0 波商店」 |

| `main.gd:868` | `_continue_endless`：`save(next_wave, ..., WAVE_START)` | ~~`CHECKPOINT_SHOP`~~ → **实际保留 `WAVE_START`** ⛔ 预判有误（现 `main.gd:920`） | 同上：通关转无尽是**直开波**，身后无商店 |
| `main.gd:1339` | `_goto_main_menu`（商店阶段）：`save(wave+1, ..., WAVE_START)` | `CHECKPOINT_SHOP` ✅（现 `main.gd:1407`） | 从菜单回游戏落在波次开场而非商店 |
| `ui/shop_ui.gd:775` | `_flush_save`：`save(_wave + 1, ..., WAVE_START)` | `CHECKPOINT_SHOP` ✅ | 商店内买完退出，回来又在波次开场 |

> ⛔ **为什么两处被推翻**：`start_run` 与 `_continue_endless` 的共同特征是
> **身后没有任何商店**（首波之前 / 通关直开波）。当时只按「恢复后想落在商店」这个愿望推，
> 忘了「`shop` 是个**指向商店的指针**，没有商店时它无处可指」。
> → 通用判据：**`shop` 只能写在「刚刚进过商店」或「马上要进商店」的位置**。
> 另外 `restore()` 加了 `wave <= 1` 降级护栏作兜底（防手改档/旧档出现 `wave 1 + shop`）。

| 位置 | 现状 | 处理 | 说明 |
|---|---|---|---|
| `main.gd:132` | `if restored_checkpoint == CHECKPOINT_WAVE_START: start_wave(...)` else `shop_ui.open(...)` | **保留双分支** | 老存档（v2 里 checkpoint 可能是 `wave_start`）必须仍能读；分支本身就是兼容层 |
| `save_run.gd:48` | `func save(..., checkpoint := CHECKPOINT_WAVE_START)` 默认参数 | 默认值改 `CHECKPOINT_SHOP` | 默认值仍是旧语义，任何漏传参的调用点都会写错 |

**结论**：`CHECKPOINT_WAVE_START` 这个常量**不删**（老档兼容 + `main.gd:132` 分支要用），
只是**不再有任何地方主动写它**。归档时在注释里写清这一点。

|---|---|---|

### 3.1 反应表补 `from` / `to`

| 位置 | 现状 | 改成 |
|---|---|---|

| `core/registry.gd:562-590` `register_reaction` | `_valid(...)` 必填 5 字段；`_apply_defaults` 补 6 个；`_string_fields` 校验 8 个 | `from`/`to` 走 `_apply_defaults` 或**单独的显式可选校验** |

⚠️ **两个必须先知道的坑**：

1. **`fire+water` 的 id 方向是反的**：`"fire+water".id == "fire_water"`，但 name 是
   「水克火 · 蒸汽爆炸」—— 与其余 9 条 `克制方_被克方` 的命名约定**相反**。
   **绝对不能改名**，因为它被三处钉死：
   - `core/sfx.gd:53` 手写 `reaction_fire_water` 音效键；`:112` `play("reaction_" + reaction_id)`
   - `smoke_test.gd:2193/2326/2414/2445` 共 4 处按 `"fire_water"` 断言
   - `enemies/enemy.gd:304` `CodexData.unlock("reaction", reaction_id)` —— 图鉴已按此 id 落盘
   → 正确做法就是**补显式 `from`/`to`**，让方向脱离 id 命名猜谜。

2. **`_string_fields` 只校验类型、不校验存在**：实现是
   `if typeof(data.get(key)) != TYPE_STRING: return false`，字段缺失时 `data.get` 返回 `null`，
   类型非法 → **直接拒登**。所以：
   - 若把 `"from"`/`"to"` 塞进 `_string_fields` 列表 → **10 条反应全部必须带这两个字段**，漏一条整条被拒（表现为"表里有、游戏里没有"）
   - 建议：走 `_apply_defaults(data, {"from": "", "to": "", ...})`，再在注册末尾做「若 from/to 为空则从 key + type 推导」的兜底
